# 成员、议题与流程修改

## 私聊和开会分别怎么用？

**追问一个人**：打开运行实例，选中节点和成员，再进入会话；例如问核对员「你依据的是哪一句？」。浏览器发送指示会显示消息状态。成员由自己的上下文作答，不需要把整个团队的聊天复制给它。

**需要不同专业意见**：在实例的协作区域查看成员和议题；让协调成员开一个清楚的议题，指定相关参与者。比如：「把版本号放标题还是正文？请开发和检视者各给一个依据。」参与者先独立回答，再交换相关意见。默认最多三轮，分歧还在就交给裁决者。到议题里看结论和行动项，不用再开一条全员共享的原生聊天。

**想暂停看看**：在团队菜单或实例页选择暂停。已经在执行的成员仍可以收尾并交回回执；主聊天不因此追加模型请求。暂停期间的私聊会先排队，恢复后由原来的成员处理，无需新建聊天。普通会话选择器默认不列出新建的私有成员；Alpha 先创建、再归档并回读确认，因此创建瞬间原生列表有一个很短的可见窗口。

**需要改变工作方向**：登记纠偏，说明新要求及受影响的任务。提交意见不等于批准应用。应用后查看哪些尝试和旧批准已过期、哪些成员实际收到通知；无关任务仍可继续。界面若显示「未送达」，不能仅因为替代成员看到了新说明就当成旧成员已收到。

## 修改流程，而不改变所有运行实例

1. **先区分工作要求和流程规则。** “这次加一段版本说明”通常是工作纠偏；“从此发布前必须有独立核对节点”才需要改流程。
2. **在草稿中设计。** 从模板打开「共享草稿 / 独立设计会话」，保存草稿并与流程设计成员讨论理由、节点和提示词。若另一方先保存，先比较新的草稿再提交；不要用旧 revision 覆盖。
3. **检查并发布。** 在图上逐个检查负责人、提示词、通过条件和返工目标。设计成员可以改草稿或提出修改；发布由你显式确认。发布新版本后，已在运行的实例保持原版本。
4. **只修改需要升级的实例。** 在目标实例中查看补丁提案，核对改动的节点、已有交付、受影响批准及需要重做的工作，然后决定是否应用。它可能等待正在执行的任务到达可切换的时点。
5. **核对结果。** 比较两个实例：应用的实例应显示新版本，未应用的仍显示旧版本。遇到 `review_required` 说明影响范围变了，需要看新提案并单独批准；系统不会扩大你原来的同意范围。

想循序试用，可以先跑[只读核对练习](quickstart.md)，再试 `bug-fix` 或 `require-development`。后两者包含开发节点，有可能改动所选项目的文件。
